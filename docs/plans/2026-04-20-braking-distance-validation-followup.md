# 后续建议：基于 Beta_list 与 V_list 的制动距离校验

日期：2026-04-20

## 1. 背景

当前第一阶段已经收敛到：
- `s1~s3` 可根据 `requirement`、`response_time`、`brake_types` 计算 `Beta_list`
- `Beta_list` 已可作为后续各制动类型校验和输出扩展的稳定输入

在 MVP 之后，建议补充一个“基于 `Beta_list` 与 `V_list` 的制动距离校验功能”，用于在各定义初速下校验不同制动类型的理论制动距离，并将结果同时用于中间分析与最终报告摘要。

## 2. 目标

新增一个后续能力，使系统可以：
- 基于 `Beta_list` 和 `V_list` 计算各制动类型在各定义初速下的理论制动距离
- 输出人可读、机可读的距离校验表
- 在最终 `report` 中汇总关键校验结论

## 3. 推荐输出形态

建议采用两层输出。

### 3.1 中间层

新增中间量，例如：
- `braking_distance_by_speed`

建议结构：

```yaml
braking_distance_by_speed:
  FSB:
    40.0: ...
    60.0: ...
    80.0: ...
  EB:
    40.0: ...
    60.0: ...
    80.0: ...
  holding_brake:
    40.0: ...
    60.0: ...
    80.0: ...
```

这个中间量用于：
- 本地调试
- 工程复核
- 后续与 requirement/技术条件做逐项比对

### 3.2 report 层

建议在最终 `report` 中加入距离校验摘要，例如：
- 各 brake type 在 `V_list` 各速度点的理论制动距离
- 是否满足技术条件
- 超限项目汇总

建议 report 中只保留高价值摘要，不必把全部推导细节都塞入 report 根层。

## 4. 推荐计算边界

建议该能力只做“基于已确定控制减速度的距离校验”，不回写上游输入，也不改变 `Beta_list`。

即：
- 输入：`Beta_list`、`V_list`
- 输出：距离表 + 校验结论
- 不参与反求 `Beta`
- 不改变既有 workflow 的上游语义

## 5. 推荐接入位置

建议作为后续独立步骤接入 `s3` 之后、最终汇总之前。

可选接入方式：

1. 在 `s3` 之后新增独立模块
   - 优点：语义清楚，直接依赖 `Beta_list`
   - 缺点：需要调整 workflow

2. 在 `s9 summarize_and_checks` 中先临时实现
   - 优点：改动少
   - 缺点：职责容易过重

推荐选项：新增独立模块。

## 6. 推荐执行方式

后续真正实现该能力时，建议由另一个 subagent 负责“比对检查”侧工作。

推荐职责拆分：
- 主实现线程：负责距离计算逻辑、契约接入、report 汇总
- 独立 subagent：负责对 `Beta_list`、`V_list`、requirement 之间的比对逻辑进行检查，重点审查：
  - 距离计算公式是否和当前业务假设一致
  - 各 brake type 的适用边界是否正确
  - report 中的校验摘要是否存在遗漏或歧义

这样做的价值：
- 避免主实现和校验逻辑由同一思路闭环，降低遗漏风险
- 让“计算”和“比对检查”职责分离

## 7. 推荐的最小后续范围

后续若进入实现，建议先做最小版本：
- 只基于 `Beta_list` 和 `V_list` 计算理论制动距离
- 先输出中间量
- report 中只增加简单摘要
- 暂不引入更复杂的附加修正项

## 8. 建议的下一步

当 `s4~s9` 主流程继续稳定后，再单独为这个能力开一个小阶段：
- 先补 spec
- 再补契约
- 再实现距离计算与 report 汇总
- 最后安排独立 subagent 做比对检查
