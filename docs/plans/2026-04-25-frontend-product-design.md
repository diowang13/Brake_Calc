# brake-calc 前端产品设计结论（V1）

> 基于 `2026-04-23-input-yaml-frontend-ui.md` 与 2026-04-25 访谈整理。
> 本文档用于冻结前端产品定义、信息架构与交互边界，供后续前端实施计划与开发使用。

## 1. 目标与边界

前端 V1 的目标不是重新定义 brake-calc 业务，而是把已冻结的 V1 输入契约、已完成的 storage/backend 能力，以及已验收的 report 口径，组织成一个适合机械设计工程师使用的中文 Web 工作台。

前端必须完成四件事：

1. 编辑完整 V1 输入配置
2. 调用 backend 做权威校验
3. 保存、打开、导入、导出配置版本
4. 运行计算并消费结构化 `report`

前端不做：

- 业务计算
- report 推导
- YAML 权威校验
- 持久化协议定义
- 超出 V1 的业务扩展

必须严格服从：

- `AGENTS.md`
- `specs/Brake_Calc_ Workflow_Spec_v1.0.md`
- 当前已冻结 V1 输入契约
- 当前已验收 report / Markdown 口径

## 2. 用户与核心使用场景

主要用户是机械设计工程师，通常没有代码背景。

核心使用场景只有两条：

1. 新建项目，从空白开始完成首轮配置并运行
2. 打开既有配置，在已有结果基础上补充后置信息或发起修订并重新计算

辅助场景：

- 导入外部 YAML 形成可编辑配置
- 导出 YAML 给业务负责人排查或留档

因此产品主入口应优先服务“新建项目”和“打开既有项目”，而不是以 YAML 文件操作为中心。

## 3. 总体产品形态

前端采用“配置工作台 + 顺序引导”的混合模式：

- 新用户可按步骤顺序完成配置
- 熟练用户可在工作台内自由跳转章节
- 结果页与配置页之间支持快速往返

推荐目录位置维持既有计划假设：`frontend/`。

## 4. 页面结构与信息架构

### 4.1 首页 / 列表页

首页主入口：

- `新建项目`
- `打开既有项目`
- `导入 YAML`（辅入口）

项目/配置列表最重要的信息：

- 项目名称 / 编号
- 最后修改时间
- `controller_type` 的业务显示名

### 4.2 新建项目初始化流程

点击“新建项目”后，不直接进入完整空白大表单，而是先走一个简短初始化流程：

1. 先填写 `project_name`、`project_code`
2. 选择 `BCU 类型 = 架控 / 车控`
3. 输入简化编组信息，用于自动生成初始 `vehicle_config`

进入工作台后：

- 默认落在“运行基础配置 / 技术条件”章节
- 初始 `vehicle_config` 由模板生成
- 用户可继续微调实例列表

### 4.3 配置工作台

工作台采用三栏结构：

- 左侧：章节导航与状态标记
- 中间：当前章节表单
- 右侧：校验错误、YAML 预览、局部运行/结果摘要

YAML 预览定位：

- 面向高级用户核对
- 不是主要编辑入口
- 不支持直接手改 YAML 作为主流程

### 4.4 章节组织

中间主表单按“计算流程”分章，而不是按技术实现分层：

1. 项目基础信息
2. 运行基础配置 / 技术条件
3. 车辆与控制器配置
4. 载荷与空簧
5. 基础制动机械参数
6. 停放校核
7. 标定
8. 电制动特性
9. 结果页

其中：

- `停放校核`
- `标定`
- `电制动特性`

都属于 V1 范围，但不应被强制纳入所有新建项目的首轮必经路径。

## 5. 新建、打开、修订、补充的流程定义

### 5.1 新建项目主路径

新建项目首轮计算的默认主路径是“先完成主制动计算”，而不是强制同时完成停放校核、标定和电制动特性录入。

因此前端要支持：

- 先完成主制动相关必填项
- 先跑出第一轮结果
- 后续再补充停放校核、标定、电制动特性

### 5.2 打开既有项目后的默认状态

对于“已运行成功”的既有项目，打开后默认进入 `只读总览`，不是直接进入可编辑状态。

总览页定位是工作台入口页，不是完整配置详情页。

总览页最重要的信息：

- 最后一次运行时间 / 状态
- 警告与自动调整
- 是否已补充停放校核

并提供三个后置补录快捷入口：

- `补充停放校核`
- `补充标定`
- `补充电空计算`

这里“电空计算”是业务侧习惯叫法；V1 产品语义仍严格落在 `electric_brake` 输入补录与摘要查看，不表示已接入主计算。

### 5.3 只读、补充、修订三种状态

前端需明确区分三种状态：

1. `只读基线`
2. `补充后置信息`
3. `正式修订`

在默认只读态下：

- 主配置章节锁定
- 左侧导航仅开放停放校核、标定、电制动特性三章
- 总览页提供三项快捷入口
- 三项快捷入口必须是明确可点击的补录动作，而不是仅显示状态

### 5.4 修订机制

若用户需要修改主配置，不能直接改当前已运行成功版本，必须显式点击 `修订`。

修订行为定义为：

- 自动基于当前版本创建一个新版本副本
- 用户在副本上编辑、保存、运行
- 原版本保持不变

修订副本必须记录：

- 来源版本
- 修订时间
- 修订原因 / 说明

V1 预置修订原因：

- 外部条件变更
- 标定更新
- 补充停放校核
- 增加电空计算

## 6. 章节级产品定义

### 6.1 运行基础配置 / 技术条件

本章应按制动业务目标组织，把技术条件与对应响应时间放在同一块里，而不是让用户在 `requirement` 和 `response_time` 两组字段之间来回对应。

组织顺序：

1. 最大常用制动
   - 平均减速度要求
   - 空走时间 `t1`
   - 冲击率 `impulse_rate`
2. 紧急制动
   - 平均减速度 / 制动距离录入模式切换
   - 空走时间 `t1`
   - 响应时间 `t2`
3. 不同初速度下的制动距离校核要求
   - 最高速度 `v0` 在本区手工录入，并默认参与校核
   - 本区只支持添加 `V_list` 中的额外待校核速度
   - 待校核速度输入框使用紧凑尺寸，约占普通输入宽度的 1/4，避免多点时撑开卡片
4. 快速制动
   - 是否启用
   - 启用后不单独显示响应时间，直接复用最大常用制动的 `t1` 与 `impulse_rate` 写入 `input.yaml`
5. 其他比例制动
   - 支持添加 `ratio_of_FSB` 类型
   - 每项录入写入 YAML 的制动类型代号 `name` 与相对最大常用制动比例
   - 若代号输入中文，按当前契约会原样写入 `brake_types[].name`；为便于后续配置引用和代码协作，界面应建议使用英文/数字/下划线代号
6. 全局黏着限制 `adhesion.mu_limit`

`adhesion.mu_limit` 是全局约束，放在本章录入，不放入停放校核章节。

制动类型交互规则：

- `FSB`、`EB` 必含
- `FB` 与自定义 `ratio_of_FSB` 的初始显示由初始化向导决定
- 进入工作台后仍可继续增减可选类型

### 6.2 车辆与控制器配置

`vehicle_config` 录入不应强迫用户从空白逐条手建实例。

推荐方式：

- 初始化阶段用简化编组信息快速生成
- 进入工作台后允许逐条微调

### 6.3 载荷与空簧

这是最高风险章节，必须优先投入解释和防错设计。

页面策略：

- 页面顶部先解释“这一页在算什么、这些值通常来自哪里”
- 关键字段旁必须有简短中文说明和单位提示
- 最关键的 1 到 2 句默认展开，详细说明折叠

章节内部顺序应按业务录入节奏重排为：

1. `车辆载荷参数录入`
2. `转向架参数录入`
3. `空簧特性输入`

#### `mass_params` 录入原则

车辆载荷参数录入不应直接暴露底层技术变量名，而应优先使用业务录入语言。

建议按 `AW0 / AW2 / AW3` 组织，每个载荷组内再区分：

- `动架称重`
- `拖架称重`

需要特别处理录入口径差异：

- `bogie_weight` 通常来自单个转向架口径
- `mass_static` 在业务资料中常见整车口径

因此前端应支持车辆载荷两种录入口径：

- 按整车录入
- 按转向架录入

交互要求：

- 用明确切换控件选择录入口径
- 默认推荐“按整车录入”
- 切换后字段标签、说明文字、口径提示同步变化
- 同页强提示：`bogie_weight` 始终是单个转向架口径

当 `controller_type = car` 时：

- 不应把质量参数改造成整车专属另一套概念
- 仍保留 bogie 类型级参数录入
- 但必须明确提示：车控模式下系统会按一车两转向架聚合

#### `转向架参数录入` 原则

本区主要承接明确按转向架口径录入的参数，例如 `bogie_weight`，并承担“车辆称重口径 vs 转向架口径”的解释作用。

#### `air_spring` 录入原则

先选输入模式，再展示对应字段：

- 特征点拟合
- 显式线性公式

不预设某一种为绝对主流默认。

若使用特征点拟合，必须强提示坐标轴单位，尤其是横轴质量单位风险：

- 压力轴：`kPa`
- 质量轴：`ton`

由于业务资料里有时会给 `kN`，此处是高风险误填点。

特征点录入时，每个点的两个坐标不应放在一个输入框中，而应拆成两个独立字段，顺序为：

1. 压力（`kPa`）
2. 质量（`ton` / `kN`）

前端设计结论倾向支持横轴单位辅助切换：

- `ton / kN`

若支持 `kN`，前端仅做录入辅助换算，不改变后端权威输入口径。该点需在实施前再次确认不突破 V1 契约边界。

### 6.4 基础制动机械参数

这是第二高风险章节，核心问题不是流程，而是“单位多、参数多、停放缸与制动缸容易混”。

因此：

- 单位必须强提示，不能只藏在 placeholder
- 页面说明需明确区分制动缸参数与停放缸参数
- 停放缸参数不得混入本章

### 6.5 停放校核

停放校核是独立章节，且默认不干扰新建项目首轮主路径。

本章定位：

- 默认服务“后置补录”
- 也支持快速回看当前是否已配置、是否完整
- 只录入 `parking_brake_check` 输入；`F_N_PB`、`F_PB`、`whole_train` 等校核结果放到结果页展示

页面结构：

1. 顶部状态摘要
2. `校核配置`
   - `required_safety_margin`
   - `static_friction_coefficient` / `xi0`
   - `n_parking_cylinders_by_car`
3. `环境条件`
   - `wind_speed_max`
   - `wind_resistance_coefficient`
   - `grade_by_load_group`
4. `停放缸参数`
   - `Fp`
   - `Fs1`
   - `Fs2`
   - `Lpi`
   - `eta_pi`
   - `Lo`
   - `eta_o`

本章不得把 `F_N_PB` 命名为输入项，也不得单独录入 `Rf`；夹钳制动几何换算使用基础制动机械参数中的 `Dw / Rf`。

### 6.6 标定

标定章节必须按 `载重工况` 组织，而不是优先按 `service_brake / emergency_brake` 组织，因为现场试验与补录流程是按载重工况展开的。

页面结构：

- `aw3_aw0`
- `aw3_aw2`

每个工况块内：

1. 先显示当前状态摘要（未配置 / 部分配置 / 已完整配置）
2. 再进入对应点表与模式编辑

本章要同时支持：

- 首次补录
- 多轮修订
- `aw3_aw0` 与 `aw3_aw2` 交替更新

车控项目的 V1.0 限制：

- 当 `controller_type = car` 时，前端不得开放 `emergency_brake` 紧急制动标定录入
- 车控 EB 的现场标定采用机械式实际 BCP 压力标定方法，V1.0 暂不接入
- 车控项目仍可补录 `service_brake` 常用/快速制动标定
- 标定页需明确提示：车控 EB 实际 BCP 压力标定 V1.0 暂不支持，需由开发人员线下处理，V1.1 接入

### 6.7 电制动特性

V1 范围内，本章的核心价值不是参与主制动计算，而是：

- 补录 `electric_brake` 输入
- 查看电机特性
- 通过图表快速理解电制动曲线

页面应轻量但直观：

- 上方展示电制动曲线
- 下方展示特性点表

## 7. 保存、校验、导入、导出、运行

### 7.1 保存

默认心智：

- 用户可随时保存草稿
- `保存` 只保存配置，不触发计算

### 7.2 运行

运行是单独动作。

点击“运行”后：

- 系统自动执行权威校验
- 校验通过才真正运行
- 运行成功后自动切换到结果页

### 7.3 导入 YAML

导入 YAML 是辅助场景，主要服务于“高级用户或业务负责人提供 YAML，工程师将其导入为系统内可编辑配置”。

导入成功后，不直接进入编辑页，而是先进入导入摘要页。

导入摘要页优先展示：

- 是否包含停放校核 / 标定 / electric_brake 等后置内容
- 是否存在导入警告
- 是否可直接运行

### 7.4 下载 YAML

下载 YAML 的主要用途：

- 发给业务负责人排查问题
- 留档
- 配置快照交接

它不是普通工程师的日常编辑入口。

## 8. 结果页设计结论

### 8.1 结果首屏优先级

结果首屏不能只围绕压力矩阵。

优先级应为：

1. 顶部摘要
2. 制动性能检查
3. 压力矩阵
4. 其他结构化结果

### 8.2 顶部摘要

最显眼的结论优先级：

1. 是否存在校验/运行警告
2. 是否触发自动调整
3. 是否满足技术条件

### 8.3 制动性能检查

第一块主结果应服务“是否满足技术条件”的判断。

需优先展示：

- 控制减速度
- 不同初速度下的理论制动距离 / 平均减速度检查

控制减速度不必单独再做一块卡片，可直接并入同一张检查表。

检查表应保留为一张总表，但：

- 不应把多个结果塞进同一个单元格
- 应拆成独立列，例如“控制减速度 / 平均减速度 / 制动距离”
- 应用更明显的底色分组或表头分组帮助定位
- 在关键结果视图中，`FSB / EB / FB` 优先显示为中文业务名称

### 8.4 压力矩阵

压力矩阵仍是核心结果，但放在制动性能检查之后。

由于不同角色关注视角不同：

- 设计者更关注按 `brake_type`
- 调试者更关注按 `load_group`

因此结果区宜提供：

- 单张矩阵表的视角切换能力

对于压力矩阵：

- 不宜拆成多个 controller 卡片分散查看
- 更适合保留为单张矩阵表，并支持两种分组视图：
  - `按载荷类型`
  - `按控制器`
- 单张矩阵必须继承 report 的 `Pressure / Dynamic Load Matrix` 口径，同时展示：
  - 动态载荷 `mass_dyn_t`（ton）
  - 标准空簧压力 `spring_kPa`（kPa）
  - 各制动类型 BCP 压力标准（kPa）
- `按载荷类型` 时，在同一载荷组下展开多个控制器，并让相同控制器使用相同底纹，便于横向追踪
- `按控制器` 时，在同一控制器下展开多个载荷组，并让相同载荷组使用相同底纹，便于纵向追踪

### 8.5 控制器开发参数展示

结果页需要显式服务控制器开发人员，不应把相关参数完全隐藏在“有标定时才出现”的逻辑后面。

因此即使项目未配置标定，结果页也应展示：

- `k_for_code`
- `BCP0_for_code`

原因：

- 这两个量本身就是控制器开发输入
- 是否做过标定，只影响其来源与解释，不影响它们作为开发参数的展示必要性

若存在标定：

- 展示最终生效的 `k_for_code`、`BCP0_for_code`
- 同时展示标定相关摘要

若不存在标定：

- 仍展示当前用于开发的 `k_for_code`、`BCP0_for_code`
- 并明确标识“当前未配置标定”或等价说明，避免误解其来源

控制器开发参数展示时，应至少区分：

- 常用制动
- 紧急制动

展示形态：

- 左侧展示控制器开发直接使用的参数值：
  - 常用制动 `k_for_code`
  - 常用制动 `BCP0_for_code`
  - 紧急制动 `k_for_code`
  - 紧急制动 `BCP0_for_code`
- 标定后，`k_for_code` 应展示为分段公式，而不是压缩成一句描述
- 右侧标定摘要应图形化表示 `k_for_code` 分段曲线，常用制动与紧急制动分开展示
- 当 `controller_type = car` 时，V1.0 不展示车控 EB 的伪 `k_eb(f)` 标定曲线、伪分段 `k_for_code` 或标定后的 `BCP0_for_code`
- 车控 EB 区域应展示限制提示：车控 EB 实际 BCP 压力标定 V1.0 暂不支持，需由开发人员线下处理，V1.1 接入

### 8.6 结果页与配置页往返

运行成功后自动进入结果页。

结果页应同时提供：

- 顶部 `返回配置`
- 章节导航直接跳转相关配置章节

## 9. 错误提示与防错设计

### 9.1 错误提示语言

必须使用中文。

### 9.2 错误提示结构

采用两层结构：

1. 顶部业务化中文结论
2. 可点击定位的字段错误清单

### 9.3 运行前失败文案

分两类处理：

- 缺失/未填：`当前配置还不能运行，请先补全以下信息`
- 格式/逻辑冲突：`配置校验失败，请修正以下字段错误`

### 9.4 错误定位方式

三层同时存在：

- 左侧章节导航显示错误状态
- 右侧错误清单支持点击跳转
- 中间字段旁显示中文错误提示

### 9.5 失败后的辅助动作

运行失败后，应在失败提示附近强调两个动作：

- 中文错误摘要
- 下载当前 YAML

便于用户把配置和错误一起发给业务负责人排查。

## 10. V1 设计取舍与优先级

前端 V1 的优先级不是“先做漂亮复杂的交互”，而是：

1. 主流程必须走通
2. 易错区必须讲清楚并做强防错

如果要取舍，优先保证以下区域的解释和防错质量：

- 载荷与空簧
- 基础制动机械参数

## 11. 对实施计划的影响

后续前端实施计划必须继承本文档，而不是回退到旧版假设。

与旧计划相比，必须显式吸收以下新增结论：

- 主流程是“新建项目 + 打开既有配置”
- 已运行成功项目默认进入只读总览
- 存在“只读 / 补充 / 修订”三种状态
- 修订必须创建新版本副本，不直接覆盖旧版本
- 停放校核、标定、电制动特性属于后置补录章节
- 结果首屏以制动性能检查优先，不以压力矩阵优先
- `mass_static` 需支持整车/转向架两种录入口径
- `air_spring` 特征点必须强提示单位风险

## 12. 待后续实施前再次确认的点

以下点已经形成产品倾向，但在真正进入实现前还需要再做一次契约/实现方式确认：

1. `mass_static` 双录入口径是前端显示层转换，还是 backend 接口显式支持两种口径
2. `air_spring` 特征点横轴是否允许 `kN` 辅助录入，以及换算职责由哪一层承担
3. 只读基线、补充后置章节、修订副本在 backend storage/API 上的状态表达方式
4. “最后一次运行状态”“是否已补充停放校核”等总览指标由哪一个 backend 接口统一提供

## 13. 原型目标与范围

## 15. 页面原型说明

### 15.1 首页 / 项目列表页

页面目标：

- 让用户快速进入“新建项目”或“打开既有项目”
- 让既有项目快速被识别

页面结构：

1. 顶部标题区
   - 页面名称
   - `新建项目`
   - `导入 YAML`
2. 搜索与筛选区
   - 项目名称 / 编号搜索
   - `controller_type` 筛选
3. 项目列表区
   - 项目名称 / 编号
   - 最近修改时间
   - `controller_type`
   - 最近运行状态简标
4. 列表行操作
   - `打开`

原型重点：

- “新建项目”和“打开既有项目”必须是主动作
- “导入 YAML”必须是辅动作，不抢主路径

### 15.2 新建项目初始化向导

页面目标：

- 减少空白表单恐惧
- 快速生成初始配置骨架

页面结构：

1. 步骤一：项目基础信息
   - `project_name`
   - `project_code`
2. 步骤二：控制器类型
   - `bogie / car`
3. 步骤三：简化编组输入
   - 例如几动几拖、总车数、推荐生成说明
4. 底部动作
   - `下一步`
   - `进入工作台`

原型重点：

- 向导必须很短
- 不能在初始化阶段塞入完整业务表单

### 15.3 只读总览页

页面目标：

- 作为既有成功项目的默认落点
- 明确区分“回看”“补充”“修订”

页面结构：

1. 顶部项目与版本信息
   - 项目名称 / 编号
   - 当前版本标识
   - 来源版本信息
   - 修订原因（如有）
2. 最近结果摘要区
   - 最后一次运行时间 / 状态
   - 警告与自动调整
   - 是否已补充停放校核
3. 后置补录快捷入口
   - `补充停放校核`
   - `补充标定`
   - `补充电空计算`
4. 主动作区
   - `修订`
   - `查看结果`
5. 左侧导航
   - 主配置章节锁定
   - 仅开放后置补录章节

原型重点：

- 用户必须一眼看懂当前默认是只读态
- “修订”和“补充后置内容”必须明显分开

### 15.4 配置工作台页

页面目标：

- 支撑完整配置编辑
- 同时支持顺序录入和自由跳转

总体结构：

1. 顶部工具栏
   - 项目名称 / 当前状态
   - `保存`
   - `运行`
   - `下载 YAML`
   - 返回总览 / 结果入口
2. 左侧章节导航
   - 章节顺序
   - 当前章节高亮
   - 完整度 / 错误状态标记
3. 中间章节表单
4. 右侧面板
   - 错误清单
   - YAML 预览
   - 局部说明 / 状态摘要

#### 运行基础配置 / 技术条件

区块顺序：

1. 本章说明
2. 最大常用制动
3. 紧急制动
4. 不同初速度下的制动距离校核要求
5. 快速制动
6. 其他比例制动
7. 全局黏着限制 `adhesion.mu_limit`

原型重点：

- 标签优先对齐业务目标，不在主标签里暴露 `requirement.FSB / requirement.EB`
- 紧急制动支持平均减速度和制动距离两种录入模式
- `V_list` 以“不同初速度下的制动距离校核要求”呈现，默认包含最高速度 `v0`，可追加待校核速度
- `FB` 是启用开关；启用后响应时间复用最大常用制动，不单独显示
- `ratio_of_FSB` 以可追加列表展示，点击“添加比例制动类型”后新增一行制动名称与比例输入

#### 车辆与控制器配置

区块顺序：

1. 编组生成结果摘要
2. 实例列表
3. 逐项微调

原型重点：

- 不让用户从纯空白逐条搭建实例

#### 载荷与空簧

区块顺序：

1. 本章顶部解释区
2. `mass_params`
3. `air_spring`

`mass_params` 原型要求：

- 先按 `powered_bogie / trailer_bogie` 分块
- 每块内按 `AW0 / AW2 / AW3` 排列
- 提供 `mass_static` 录入口径切换
- 明确提示 `bogie_weight` 是单个转向架口径

`air_spring` 原型要求：

- 先选模式，再显示对应字段
- 特征点模式下强提示坐标轴单位
- 若支持 `ton / kN` 辅助切换，需在原型中表现切换位置

原型重点：

- 这是最高优先级验证页
- 必须重点看用户是否还会把整车/转向架口径和 `ton / kN` 混掉

#### 基础制动机械参数

区块顺序：

1. 本章顶部解释区
2. 基础制动缸参数
3. 条件显示项
   - `Dw`
   - `Rf`
4. 单位提示区

原型重点：

- 停放缸参数不能混进本页
- 单位必须足够醒目

### 15.5 结果页

页面目标：

- 先判断结果是否可信、是否满足业务关注点
- 再下钻看压力结果和其他明细

页面结构：

1. 顶部摘要区
   - 运行状态
   - 警告
   - 自动调整
2. 制动性能检查区
   - 控制减速度
   - 不同初速度下的理论制动距离 / 平均减速度检查表
3. 压力矩阵区
   - 紧凑总表
   - 视角切换
4. 其他结果区
   - 控制器开发参数
   - 标定摘要
   - 停放校核结果摘要：展示 `F_N_PB`、`F_PB`、`whole_train` 和逐载荷组通过情况
   - V1.0 暂不在结果页展示电制动摘要；电制动主要服务设计阶段，保留在对应补录章节内查看
5. 页面动作
   - `返回配置`
   - 导航跳转至相关配置章节

原型重点：

- 结果首屏不能先掉进压力矩阵
- “制动性能检查是否比压力矩阵更符合业务优先级”是本轮关键验证点
- 即使没有标定，结果页也必须能看到 `k_for_code` 和 `BCP0_for_code`

### 15.6 标定页

页面目标：

- 支撑首次补录与多轮更新

页面结构：

1. 页面顶部状态摘要
2. `aw3_aw0` 工况块
   - 当前状态
   - service / emergency 配置区
   - 点表编辑区
3. `aw3_aw2` 工况块
   - 当前状态
   - service / emergency 配置区
   - 点表编辑区
4. 页面动作
   - `保存`
   - `运行`

车控项目限制：

- `controller_type = car` 时，标定页只开放 `service_brake` 常用/快速制动标定
- `emergency_brake` 紧急制动标定区应隐藏或禁用
- 禁用时需明确说明：车控 EB 实际 BCP 压力标定 V1.0 暂不支持，需由开发人员线下处理，V1.1 接入
- 不允许前端把车控 EB 套用架控的 `k_for_code / BCP0` 曲线标定逻辑

原型重点：

- 先按载重工况，而不是先按制动模式
- 用户要能看懂“这组工况现在缺什么”

### 15.7 停放校核页

页面目标：

- 适配后置补录
- 让用户先判断“当前做没做、差什么”

页面结构：

1. 页面顶部状态摘要
2. 校核配置区
3. 环境条件区
4. 停放缸参数区
5. 页面动作
   - `保存`
   - `运行`

原型重点：

- 校核配置、环境条件和停放缸参数要明显分区
- 页面要明显体现这是独立章节，不是基础机械参数的附属区
- 本页只做输入补录，不展示 `F_N_PB / F_PB / whole_train` 结果
- `adhesion.mu_limit` 属于全局黏着限制，放在“运行基础配置 / 技术条件”

### 15.8 电制动特性页

页面目标：

- 轻量查看电机特性
- 不误导为已参与主制动计算

页面结构：

1. 页面顶部状态摘要
2. 电制动曲线区
3. 特性点表区
4. 页面说明
   - 当前仅做输入补录和摘要展示

原型重点：

- “看曲线”必须是第一视觉重心

### 15.9 导入摘要页

页面目标：

- 让用户导入后先确认导入结果是否可用

页面结构：

1. 导入结果摘要
2. 后置内容识别结果
   - 是否包含停放校核 / 标定 / electric_brake
3. 导入警告区
4. 可运行性判断
5. 页面动作
   - `进入工作台`
   - `查看总览`

原型重点：

- 不应导入成功后直接把用户扔进大表单

### 15.10 修订创建弹窗

页面目标：

- 让“修订”成为显式、可追踪的版本动作

页面结构：

1. 来源版本信息
2. 修订原因选择
3. 修订说明输入
4. 确认提示
   - 将创建新版本副本
   - 原版本不会被修改
5. 页面动作
   - `创建修订版本`

原型重点：

- 必须让用户清楚这不是直接改原版本

## 19. 前端实施计划

本章节用于承接前文已经冻结的产品结论与原型评审结果，指导后续 `frontend/` 的正式开发。

### 19.1 实施前提

前端正式开发前，默认以下条件已满足：

- storage schema 已稳定
- backend API contract 已稳定
- import path 已能返回可编辑 `form_state`
- run path 已能返回 V1 结构化 `report`

若以上条件未满足，则前端开发只能停留在静态原型或局部假数据联调阶段，不应进入正式页面交付。

### 19.2 原型冻结结论

进入开发前，以下原型结论视为当前冻结基线：

- 首页采用双主入口：
  - `新建项目计算`
  - `打开既有项目`
- 首页列表展示：
  - 项目名称 / 编号
  - 最后修改时间
  - `车控 / 架控`
  - 最近运行状态
- 新建项目采用 2 步初始化向导：
  - 项目基础信息
  - 初始化配置
- 初始化阶段关键业务字段包括：
  - 项目名称
  - 项目编号
  - 报告获取邮箱
  - 备注
  - `BCU 类型`
  - 总车数 / 动车数 / 拖车数
- 已运行成功项目默认进入只读总览页
- 只读总览页必须清楚区分：
  - 查看结果
  - 修订主配置
  - 补录停放校核 / 标定 / 电空计算
- 工作台采用三栏结构：
  - 左侧章节导航
  - 中间当前章节
  - 右侧说明 / 错误 / YAML
- `载荷与空簧` 页结构冻结为：
  - `车辆载荷参数录入`
  - `转向架参数录入`
  - `空簧特性输入`
- 结果页结构冻结为：
  - 顶部摘要
  - 制动性能检查
  - 压力矩阵
  - 控制器开发参数
  - 其他结果块

### 19.3 目录与工程骨架

前端目录位置按既有结论采用：

- `frontend/`

建议最小骨架如下：

```text
frontend/
  prototype/              # 当前低保真原型
  src/
    app/                  # 应用壳、路由、页面装配
    pages/                # 首页、总览页、工作台页、结果页
    features/             # 按业务域拆分的页面逻辑
    components/           # 通用 UI 组件
    form-state/           # FormState、映射、默认值、转换
    api/                  # validate/save/load/import/export/run client
    mock/                 # 原型期或联调前的假数据
    styles/               # 主题变量和全局样式
```

实现要求：

- 保持 `FormState` 与 backend contract 明确分层
- 不让页面直接拼接 YAML
- 不让结果页自己推导业务结果

### 19.4 页面开发顺序

建议按下面顺序推进，而不是按字段或组件零散开发。

#### 阶段 1：应用骨架

目标：

- 建立前端工程
- 能切换主要页面
- 能承载后续假数据和真实 API

内容：

- 应用壳
- 基础路由
- 全局样式变量
- 页面容器

#### 阶段 2：首页 / 列表 / 初始化向导 / 只读总览

目标：

- 打通用户最外层主流程

内容：

- 首页 / 项目列表页
- 新建项目初始化向导
- 只读总览页
- 修订创建弹窗

原因：

- 这几页决定用户是否能进入系统并理解版本状态
- 也是后续接入真实数据前最适合先落地的页面

#### 阶段 3：配置工作台壳层

目标：

- 先打通工作台结构，再填具体章节

内容：

- 顶部工具栏
- 左侧章节导航
- 右侧说明 / 错误 / YAML 标签区
- 中间单章节显示机制

#### 阶段 4：主配置章节

开发顺序建议：

1. `运行基础配置 / 技术条件`
2. `车辆与控制器配置`
3. `载荷与空簧`
4. `基础制动机械参数`

原因：

- 这是新建项目主路径
- 也是第一轮正式可运行配置最关键的部分

#### 阶段 5：后置补录章节

开发顺序建议：

1. 停放校核
2. 标定
3. 电制动特性

原因：

- 这三块在产品上已明确定义为后置补录
- 可以晚于主路径，但必须保留独立章节身份

#### 阶段 6：结果页与导入摘要页

目标：

- 打通运行后回显
- 打通导入后的确认流转

内容：

- 结果页
- 导入摘要页
- 错误摘要与下载 YAML 行为

### 19.5 API 对接顺序

不建议一开始就并发接所有接口，建议按用户主路径逐步接入。

#### 第一步：只读与列表类接口

- 项目列表
- 项目详情 / 总览

目标：

- 先让首页和总览页脱离假数据

#### 第二步：配置读写类接口

- `GET /api/configs/{input_config_id}`
- `POST /api/configs`
- `GET /api/configs/{input_config_id}/download`

目标：

- 打通工作台的加载、保存、下载

#### 第三步：校验与导入

- `POST /api/configs/validate`
- `POST /api/configs/import-yaml`

目标：

- 打通运行前权威校验
- 打通导入摘要页

#### 第四步：运行

- `POST /api/configs/{input_config_id}/run`

目标：

- 打通结果页
- 打通从工作台到结果页的主闭环

### 19.6 高风险实现点

以下点必须单独看待，不应作为普通表单开发处理。

#### 1. 录入口径联动

`载荷与空簧` 页里：

- `按整车录入`
- `按转向架录入`

不仅要切换说明文字，还要切换字段名称与口径提示。不能只切换开关状态，不改字段文案。

#### 2. 空簧单位辅助换算

若前端支持 `ton / kN` 辅助换算：

- 必须清楚标识“仅前端辅助换算”
- 进入 API 前必须落回权威输入口径
- 不得 silently 改写用户认知

#### 3. 只读 / 补录 / 修订三种状态

这不是简单的按钮显隐，而是页面权限与流程状态问题。

必须保证：

- 已运行成功版本默认只读
- 补录章节与修订主配置有明确边界
- 修订创建新版本副本，不直接覆盖旧版本

#### 4. 压力矩阵视图

压力矩阵不能退化为普通大表或散落卡片。

必须保留：

- `按载荷类型`
- `按控制器`

两种单表分组视图，并使用稳定底纹策略帮助比对。

#### 5. 结果页参数来源说明

即使没有标定，也必须展示：

- `k_for_code`
- `BCP0_for_code`

并明确说明其来源于基础计算结果，而不是标定结果。

车控项目例外：

- 当 `controller_type = car` 时，V1.0 不展示车控 EB 的标定后 `k_for_code / BCP0_for_code`
- 车控 EB 应展示“未自动标定 / 需线下确认”的限制状态
- 仍可在压力矩阵中展示 EB 基础压力结果，但不得包装成已完成的 `emergency_brake` 标定结果

### 19.7 验证与测试要求

前端开发阶段不应只做视觉验收，至少要覆盖以下验证层次。

#### 1. 页面结构测试

覆盖：

- 首页
- 初始化向导
- 只读总览
- 工作台壳层
- 结果页

目标：

- 防止大结构回退

#### 2. 关键交互测试

覆盖：

- 初始化向导步骤推进
- 只读态与修订态切换
- 补录入口跳转
- 工作台章节切换
- YAML / 错误 / 说明标签切换

#### 3. 高风险表单测试

重点覆盖：

- `载荷与空簧` 的录入口径切换
- `ton / kN` 辅助换算入口
- 空簧特征点双字段录入
- `基础制动机械参数` 单位提示与条件显示

#### 4. 结果展示测试

重点覆盖：

- 制动性能检查表列结构
- 压力矩阵两种视图
- `k_for_code / BCP0_for_code` 在无标定时仍显示

#### 5. 联调验证

最少完成以下链路：

1. 新建项目
2. 保存配置
3. 校验配置
4. 运行计算
5. 查看结果
6. 下载 YAML

### 19.8 分阶段提交建议

建议采用小步提交，而不是长时间堆积一整个前端分支。

推荐提交顺序：

1. `feat(ui): scaffold frontend app shell`
2. `feat(ui): add home list and project initialization flow`
3. `feat(ui): add readonly overview and revision entry`
4. `feat(ui): scaffold config workbench layout`
5. `feat(ui): add run and controller configuration forms`
6. `feat(ui): add load and air spring forms`
7. `feat(ui): add base brake mechanical forms`
8. `feat(ui): add parking calibration and electric brake forms`
9. `feat(ui): add result and import summary views`
10. `test(ui): cover high-risk form and result flows`

### 19.9 进入正式开发的起点

若本文件在产品结论、原型说明、实施计划三个层面都已确认，则下一步默认进入正式开发，而不是继续扩写文档。

正式开发的第一任务建议为：

- 建立 `frontend/` 工程骨架
- 把当前 `prototype/` 中已经验证过的页面结构翻译成真实页面壳
- 先不接全部业务细节，优先落首页、总览页、初始化向导、工作台外壳
